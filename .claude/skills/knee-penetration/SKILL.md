# 膝の貫通: 検出・理解・修正

**検出は自動化できる。修正は自動化できない。** ここを混同しないこと。
数値で検出 → 解剖学的に原因を理解 → 限られた選択肢から選ぶ → 数値で合否、という流れで進める。

関連: ポーズデータ全般の読み方は `human-pose` スキルを参照。

## 1. まず自動検出する

```bash
node tools/survey-knee-poses.mjs --threshold 1.0
```

全ポーズ × 全モデル(anatomy/female/male2) × 左右で、膝内角と超過貫通(頂点数・最大cm)を測り、
貫通が大きい順に並べる。**これが問題ポーズの一次情報**であり、ここを起点にする。

個別に詳しく見るとき:

```bash
# 1ポーズを測る
node tools/measure-knee-penetration.mjs public/models/male2.glb \
  --pose src/data/poses/male2/female_action_pose_001.json --side both

# 純粋な膝曲げで角度を振って傾向を見る(FootIK無し)
node tools/measure-knee-penetration.mjs public/models/male2.glb --bend 45 --side L
```

コマンドの詳細と出力の読み方は `references/commands.md`。

### 判定の基準

| 最大超過貫通 | 扱い |
|---|---|
| < 1 cm | 合格。実機でほぼ見えない |
| 1〜3 cm | 要対策 |
| > 3 cm | 黒い穴としてはっきり見える。優先対応 |

膝内角45°未満は深屈曲で、**この領域に入ると必ず出る**と思ってよい。

## 2. なぜ起きるか（人体の構造として理解する）

### 本物の膝で何が起きているか

深く膝を曲げると、**ふくらはぎと太腿の軟部組織どうしが接触して押し合う**（thigh-calf contact）。
筋肉は潰れて横に逃げ、接触面で圧縮される。正座やしゃがみの可動域が135〜150°で止まるのは、
骨や靭帯だけでなくこの**軟部組織の詰まり**が効いているため。

つまり本物の脚では、ふくらはぎは太腿に**ぶつかって止まり、外へ膨らむ**。

### 3Dで何が起きているか

リニアブレンドスキニング（LBS）は**体積を保存しない**。頂点は骨の重み付き変換で動くだけで、
「ぶつかって止まる」も「潰れて外へ逃げる」も起きない。だから止まらずに**そのまま貫通する**。

さらにこのモデル固有の事情がある。

- ARPリグの**膝のスキンピボットが前寄り**（断面の前から24〜28%）
- 解剖学的な屈曲軸は膝蓋骨の後方、断面の**中央〜やや後方（45〜55%）**が妥当
- ピボットが前にあるぶん、曲げたときにふくらはぎ後面が**大きな半径で太腿へ振り込む**

これが「同じ角度でも実物より深く潜る」理由。

### ここから導かれる方針

- **骨の角度は正しい。** リターゲット精度は平均0.13°、膝内角はMixamo正解と一致（`docs/cowork_brief_knee.md` §3）。
  角度をいじって直す問題ではない
- **曲げを浅く制限しても解決しない。** 貫通の深さは45°付近で飽和する（同 §2）
- 必要なのは、**スキニングが再現できない「接触して外へ逃げる」変形を足すこと**。
  だから対策は morph target（シェイプキー）の系統になる

## 3. 修正の進め方

2026-08 時点で、2案が検証途中。**新しい案を考える前に、この2案の状態を確認すること。**

### 案B: 再ピボット morph（実装が最も進んでいる）

スキンピボットだけを解剖学的な中央へ寄せる。骨の位置・骨長・IKは一切変えない。
CPU検証では**貫通が約1/4**まで減っている。

- 実装: `src/viewer/KneeCorrective.ts`（`driveKneeCorrectives` が influence を駆動）
- morphを焼く: `node tools/build-knee-repivot.mjs <in.glb> <out.glb>`
- CPU上で先に効果を見る: `node tools/test-knee-repivot.mjs <arp.glb> <pose.json> --side L`

注意: `KneeCorrective.ts:124-125` に `__kneeDbg` を globalThis へ出す**一時デバッグが残っている**。
「確認後に削除する」と書かれているので、完了時に消すこと。

### 案A: 角度駆動の補正シェイプキー（PSD）

深屈曲の参照ポーズで貫通ぶんを押し戻したデルタを焼き、膝内角に応じて influence を駆動する。

- morphを焼く: `node tools/build-knee-corrective.mjs <in.glb> <out.glb> --side L --pose <pose.json>`
- 角度をまたいだ汎化を見る: `node tools/sweep-knee-influence.mjs <model.glb> --side L --morph kneeCorrective_L`
- 全ポーズで駆動を評価: `node tools/eval-knee-driver.mjs <multiMorph.glb> --model-id male2`

この案の**未確定事項**は `eval-knee-driver.mjs` の冒頭に書かれている:
「角度駆動だけで全ポーズ<1cmに届くか（＝ひねり残差の実害）」。
膝の角度が同じでも脚のひねりが違えば貫通の出方が変わるため、角度1軸の駆動で足りるかが論点。
**まずこれを数値で確定させてから、morphの枚数や刻みを決める。**

### 最後の手段

どうしても数値が届かないポーズは、`src/data/poses/pose-index.json` の該当項目に
`"hidden": true` を付けて一覧から外す。**これは対策ではなく回避**なので、
`survey-knee-poses.mjs` の結果とセットで「なぜ外したか」を残すこと。

## 4. 合否判定（必ず数値で）

**目視だけで「直った」と判断しない。過去に誤判定した実績がある。**

### 必須ライン

- 最大貫通 **1cm 未満**（現状6cm）
- 貫通頂点数が現状の **1/10 以下**
- **3体すべて**（anatomy / female / male2）で達成

### 副作用チェック（省略禁止）

膝ピボット移動の失敗は、ここを見落として起きた。

- 脚を伸ばした立ち・歩きで**膝の形が変わっていないか**
- **骨長・プロポーション**が変わっていないか
- リターゲット精度が悪化していないか（現状 平均0.13° / 最大0.67°）
- **FootIKの接地**が崩れていないか
- **ポーズを何度も切り替えて状態が蓄積しないか**。`BendSmoother` で蓄積バグの実績がある。
  1回適用しただけの検証では見逃す。連続切替を10回以上して同じ数値になるか確認する

### 目視で見るときの必須事項

- **裏面カリングを必ず有効にする。** 裏面を塗ると、アプリで黒い穴に見える貫通が
  正常な面として描かれ、問題が無いように見える（実際に一度これで誤判定した）
- 深屈曲では、ふくらはぎと太腿が**接触して押し合っているのが正しい**。
  隙間がぱっくり空いているのは過補正で、これも不自然
- 膝の折れ位置が関節からずれていないか（`BendSmoother` を撤去した理由がこれ）

## 5. 再試行禁止（検証済み・不採用）

`docs/cowork_brief_knee.md` §4。**これらを再提案しない。**

| 対策 | 結果 |
|---|---|
| DQS（双対クォータニオンスキニング） | ほぼ無効。1600→1599、最大深さ同一 |
| ウェイト平滑化 | 実質無効。1600→1521。実機でも効果なし |
| 膝ピボットを後方へ移動（骨ごと） | 数値は改善したが**実機で悪化**。骨長とプロポーションが崩れた |
| BendLimit（屈曲角クランプ） | 不採用。折れ位置が不自然。深さは45°で飽和するので効かない |
| BendSmoother（曲げの分散） | 不採用。折れ位置がずれる。FRACTION=0 済み |

また、**較正値をコードにハードコードしない**。バインド姿勢・寸法・足首高は
`loadModelCalib()` がGLBから自動実測する設計。

## 6. 進め方の作法

- **1ファイル・1箇所ずつ**変更し、都度測る。まとめて変えると原因が特定できなくなる
- 数値が必要な場面では**推測でなく実測値**を出す（実GLB・実FBXから測る）
- 肘・脇にも同種の問題が起きうる。膝で確立した手順をそのまま流用できる
