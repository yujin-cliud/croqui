# 人体ポーズの読み方・検証・作成

Croquiのポーズは「人体としてどう見えるか」が製品価値そのもの。数値が通っていても人体として
破綻していれば不良品になる。このスキルは、ポーズJSONを人体として扱うための前提と手順をまとめる。

## 最初に理解すべき大前提

### rotation は「角度」ではなく「バインド姿勢からの差分」

```json
"lowerLeg_L": { "rotation": [0.16, 0.3, 2.378] }
```

この3値は **オイラー角 XYZ・ラジアン**だが、**絶対的な関節角度ではない**。
`PoseApplier.ts:30` が `bone.quaternion = bind × delta` として適用する差分（delta）であり、
基準となる bind は GLB のレスト姿勢（`BoneMapper.ts:18` が実測して保存）。

したがって次はすべて誤りである。

- ❌ `2.378 rad = 136°` だから膝が136°曲がっている
- ❌ 値が `[0,0,0]` だから関節がまっすぐ
- ❌ Y成分が大きいから横に開いている

**数値だけを見て姿勢を語ってはいけない。** 必ず下の「角度の測り方」で実測する。

補足:
- `bones` に無いボーンは delta=恒等、つまりバインド姿勢のまま（`PoseApplier.ts:27-29`）。
  importer は `|回転| < 0.005 rad` を省くので（`tools/import-mixamo/import-mixamo.mjs:52`）、
  「記載が無い＝意図的にレスト」である。
- 対応ボーンは50ロール（胴5・首頭2・肩2・腕6・脚6・指30）。一覧は `src/types/Pose.ts:24`。
- 同じポーズIDでも **モデル(体型)ごとにバインドが違うので数値が違う**。実体は
  `src/data/poses/<modelId>/<file>.json` に焼き分けてある（`anatomy` / `female` / `male2`)。
  ルート直下の `standing_001.json` 等は後方互換の旧データ（`PoseLoader.ts:14-27`）。
  **1体だけ直して終わりにしない。3体そろえる。**

### 見た目の最終形は FK のままではない

```
applyPose(bind×delta)  →  applyBendSmoothing  →  applyFootIK  →  applyArmIK
```

`PoseApplier.ts:34-36`。特に FootIK は **腰を上下にシフトし、床付近の足を床へ貼り付ける**
（`FootIK.ts:52-80`）。よって:

- JSONのFKだけを見て「足が浮いている/めり込んでいる」と判断してはいけない
- 足首が接地高+0.1m 以内なら接地扱いで補正が入る（`PLANT_THRESHOLD`、`FootIK.ts:13`）
- 空中ポーズは `noFootIk: true` で補正を止める（`FootIK.ts:45`）
- 手が腰などに触るポーズは `ik.hand_L/hand_R` の目標点へ ArmIK が届かせる

## 角度の測り方（唯一の正しい方法）

**ワールド空間の関節位置から測る。** オイラー値からは測らない。

関節の内角（このプロジェクトの標準的な言い方）:

```
内角 = acos( normalize(S - K) · normalize(A - K) )
  S = 近位ボーンのワールド位置   (膝なら upperLeg)
  K = 関節のボーンのワールド位置 (膝なら lowerLeg)
  A = 遠位ボーンのワールド位置   (膝なら foot)
```

実装の正典は `tools/survey-knee-poses.mjs:70`。

- **内角 180° = まっすぐ**、小さいほど深く曲がる
- 膝の内角 37° は「かなりの深屈曲」（`docs/cowork_brief_knee.md` の Female Action Pose）
- 屈曲角で言う場合は `屈曲 = 180° - 内角`

ARPリグの脚では **屈曲軸はボーンのローカルZ** （`tools/measure-knee-penetration.mjs:188-191`。
リターゲット結果の lowerLeg デルタがZ支配であることから実測で決めた）。

### 使えるツール

いずれも Node が要る。このコンテナには node が無いので、**実行はWindows側で**行う。

| 目的 | コマンド |
|---|---|
| 姿勢をスティックフィギュアSVGで見る | `node tools/import-mixamo/validate-pose.mjs <poseId>` |
| 膝の貫通を1ポーズ測る | `node tools/measure-knee-penetration.mjs <model.glb> --pose <pose.json> --side both` |
| 純粋な膝曲げで角度を振る | `node tools/measure-knee-penetration.mjs <model.glb> --bend 45 --side L` |
| 全ポーズ×全モデルを一括調査 | `node tools/survey-knee-poses.mjs --threshold 1.0` |
| Mixamo FBX から作り直す | `npm run import:poses -- --force` |

`validate-pose.mjs` の限界を承知しておくこと: これは**プリミティブ版マネキンの寸法と
bind=恒等を仮定した近似**（`tools/import-mixamo/validate-pose.mjs:15-24`）で、実機のARP GLBとは
厳密には一致しない。ざっくりした姿勢確認には使えるが、**合否判定の根拠にはしない**。
数値の根拠が要る場面では実GLBを読む `measure-*` / `survey-*` 系を使う。

## 人体として破綻していないかの判定

可動域の一覧は `references/joint-ranges.md` を参照。まず次の「絶対にありえない」から見る。

- **膝が前に曲がっている**（内角が180°を明確に超える／屈曲方向が逆）
- **肘が逆に曲がっている**（前腕が上腕の後方へ折れる）
- **膝・肘に大きなねじれ**がある。どちらも回旋はほぼ持たない関節（膝は屈曲時に±10〜20°まで）
- **首や体幹が可動域を大きく超えて回っている**
- **左右が入れ替わっている**（`_L` と `_R` の取り違え。リターゲットのミラー事故で起きる）
- **足首が膝の回旋を肩代わりしている**（つま先だけ不自然に外/内を向く）

次に自然さを見る。

- 支持脚と重心: 片足立ち・コントラポストで、骨盤が支持脚側に上がり体幹が反対へ傾いているか
- 肩と骨盤のねじれ方向が歩行として整合しているか（歩きは通常たすき掛け）
- 腕が体幹にめり込んでいないか、手が太腿を突き抜けていないか
- 指がすべて完全伸展のまま（＝データ欠落）になっていないか

### 角度が原因だと決めつけない

リターゲット精度は **セグメント向き誤差で平均0.13°・最大0.67°**、膝内角はMixamo正解と一致することが
実測済み（`docs/cowork_brief_knee.md` §3）。**骨の角度は正しい**。見た目が破綻しているなら、
まず疑うのはスキニング・メッシュ・IK側であって、ポーズJSONの数値ではない。

## ポーズを作る・直すとき

数値を手で当てるのは、delta がボーンのレスト基準であるため直感が効かない。次の順で進める。

1. **可能なら Mixamo から取り込む**（`npm run import:poses`）。手書きは最後の手段
2. 手で直す場合も **1関節ずつ**。1ファイル・1箇所を変えて、都度測って確認する
3. 変更後は必ず実測する（上のツール）。**目視だけで確定しない**
4. **3モデルすべて**（anatomy / female / male2）で確認する
5. `pose-index.json` への登録を忘れない。破綻していて出したくないポーズは `hidden: true`
6. タグは `src/data/tags.json` のカテゴリ（姿勢／向き／動き）の語彙から選ぶ

やってはいけないこと:

- レンジ外の値を「見た目が合うから」で入れる。別のモデルで破綻する
- FootIK/ArmIK が直してくれる前提でFKを雑にする。IKが効くのは接地足と指定した手だけ
- 1モデルだけ直して差分を放置する

## スクリーンショットでの目視QA

過去に **目視で「直った」と誤判定した事例がある**（`docs/cowork_brief_knee.md` §6）。
画像で見るときの必須事項:

- **裏面カリングを必ず有効にする。** 裏面を塗ると、アプリで黒い穴に見える貫通が
  正常な面として描かれ、問題が無いように見える。実際に一度これで誤判定している
- 貫通は**黒く落ち込んだ穴**として現れる。膝の裏、脇、股関節まわりを重点的に見る
- 正面・側面の2方向は最低限見る。片方向だけでは奥行き方向の破綻を見落とす
- 「見た目OK」は仮説にすぎない。**合否は数値で出す**（最大貫通1cm未満・貫通頂点数が1/10以下）

副作用の確認も目視QAの範囲（同§6）:

- 脚を伸ばした立ち・歩きで膝の形が変わっていないか
- 骨長・プロポーションが変わっていないか
- FootIKの接地が崩れていないか
- **ポーズを何度も切り替えて状態が蓄積しないか**（`BendSmoother` で蓄積バグの実績あり。
  1回適用しただけの検証では見逃す）

## 既知の地雷（再試行禁止）

膝の貫通について、以下は検証済みで**不採用**。再度提案しない（`docs/cowork_brief_knee.md` §4）。

| 対策 | 結果 |
|---|---|
| DQS（双対クォータニオンスキニング） | ほぼ無効（貫通1600→1599） |
| ウェイト平滑化 | 実質無効（1600→1521） |
| 膝ピボットを後方へ移動 | 実機で悪化。骨長とプロポーションが崩れた |
| BendLimit（屈曲角クランプ） | 不採用。貫通の深さは45°で飽和するので効かない |
| BendSmoother（曲げの分散） | 不採用。折れ位置が不自然。FRACTION=0 済み |

また **較正値をコードにハードコードしないこと**。バインド姿勢・腰の寸法・足首高・手の基底は
`loadModelCalib()` がGLBから自動実測する設計になっている。
